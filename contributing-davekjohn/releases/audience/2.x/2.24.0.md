# Release notes v2.24.0 🚀

**Date:** 2026-08-15  
**Type:** Minor  
**For whom:** the organisation. No change in this release reaches a reader outside it, so there is no consumer section.

The audit backlog cleared: live site fixes, gates that really block, and docs that match the machinery

## What it is worth

This release is one week of audit work: 54 changes that started as 56 findings against a site nobody
had systematically checked. Fifty-five of those findings are closed. What it is worth falls into three
parts, and only the first is visible on the site.

**Visitors were losing things nobody could see them lose.** The listen page rendered as an empty shell
in the static HTML, so all 78 mix links were invisible to search engines while the page looked fine in a
browser. Every one of the site's 84 URLs pointed its canonical and `og:url` at a domain that redirects,
which is the one signal search engines are asked to trust above the address they arrived on. The site
declared itself English to browsers and to Google while every word on it is Dutch — so screen readers
read Dutch copy in an English voice, on a site whose whole purpose is being found locally. Two mixes
played the wrong audio and one played none at all: it had been returning 404 for an unknown length of
time, the page built, the link was there, and only somebody who pressed play would ever know. Booking
requests arrived incomplete. The contact address sat scrapeable in plain text on six pages, behind a
protection component that had been imported and then never used. None of these announce themselves;
they were found by looking.

**The cost of the next change went down, and that is the durable half.** The repo went from no automated
test at all to 213 tests across 16 suites, run locally and again on every pull request by a CI gate that
did not exist a week ago. Lint became a real gate rather than a habit: 37 errors and 8 warnings went to
zero, and the count is now enforced instead of compared. The build gate learned to check the page count,
so the specific failure that took the listen page down is one a machine now catches. The Node version is
pinned in a way that actually refuses the wrong one. The dangerous operations moved into the permission
layer that travels with the repo rather than living only in one machine's ignored settings file. Eight
npm vulnerabilities are gone, including one in Next itself. The practical effect: a change that used to
be safe only if the person making it remembered the right things is now safe because the repo checks.

**The documentation stopped disagreeing with the machine.** Roughly a third of the entries in this
release are corrections to statements that were confidently wrong — a release workflow that described a
manual route while a script did the work, a claim that Tailwind was in use when it had never generated a
single class, a branch-protection description that overstated what the ruleset holds back, a field spec
that contradicted the code it specified. Wrong documentation is more expensive than none, because it is
acted on. Every correction in this release carries the measurement that settled it, so the next reader
inherits the evidence rather than the assertion.

**What it cost to produce.** The cut itself — the integrity gate, the full test suite, the generated
notes, the commit and the tag — ran in **3 minutes**, of which the gates were the bulk. Getting from
there to a published release took a further **33**: writing this document, putting it through the same
checks and review every other change goes through, and publishing the release with its two attachments.
The whole run, from starting the cut to the release being live, was **36 minutes**, and five sixths of
that was writing and checking rather than machinery. The week of work behind it is not in that number.

## What was still open at this release

One finding out of 56 was not closed: **all 25 Full mixes still stream from the legacy storage bucket**,
while the field spec described a single active bucket. The spec was corrected to match reality, but the
files themselves were not moved, because moving them means re-uploading audio — that step sits with
Dave, not with the repo. Tracked as issue #68.

Two decisions were deliberately left open rather than taken. **Whether site work should keep waiting for
a human before merging** is now a genuinely open question rather than a settled one: every pull request
gets a Netlify deploy preview, so the change can be looked at before it goes live instead of after. The
argument for keeping the wait also survived this release intact — no gate can show that a page looks
right. **Whether to add a second branch-protection ruleset without an admin bypass** was raised and
declined for now, because such a ruleset would block the release process's own push to the trunk.

Both are settings decisions, and both sit with Dave.
